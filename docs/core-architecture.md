# 调度核心架构与实现边界

状态：`internal/core` 已实现可测试的纯调度领域状态转换，包括容量、准入、观测栅栏、任务合并、用户活动、送达验证与恢复。网络、存储提交和 CPA 生命周期仍通过外部适配层接入；核心包本身不发送请求。

## 1. 模块职责

| 文件 | 职责 |
| --- | --- |
| `types.go` | 账号、凭据代际、窗口证据、持久化基线、触发意图、合并任务、预约、用户活动 |
| `ports.go` | Host/Store/Clock/Random 边界；这些是本项目提议的端口，不是声称存在的 CPA RPC |
| `capacity.go` | 对参与账号去重，计算 `ceil(U*r)` 与每日最低目标，扣除可用容量和预约 |
| `admission.go` | 纯发送前检查；不产生预约、不写盘、不调用宿主 |
| `reducer.go` | 账号同步、字段级观测接受、稳定周期事件、请求绑定、发送意图、结果验证与恢复 |
| `*_test.go` | 名额去重、自身预约、夜间例外、周优先、观测过期、有效窗口阻挡、超时恢复抑制、合并成熟事件 |

调度协调器、持久化适配器、CPA 宿主适配器以及管理页面应使用 reducer，不直接重写上述领域规则。核心只用稳定 AccountID 和 CredentialGeneration 引用账号，不接收原始 token。宿主正常路由不由本插件改变。

## 2. 窗口证据与本地到期事件

`WindowBaseline` 是持久化且稳定的本地计时依据；`WindowEvidence` 是某次观测的分类。两者必须分开：观测返回的零用量与移动的未来时间可能只是未激活占位，不得把它反复写成新基线。

| 状态 | 含义与发送限制 |
| --- | --- |
| unknown | 信息缺失、过期或不能可靠分类；先观测，不生成 |
| inactive | 适配器有正向证据证明未激活；零用量自身不是证据 |
| active | 已确认启动且当前时间小于重置时间；所有任务禁止生成 |
| expired | 新鲜观测确认旧边界过去；重置时间必须确实在过去 |

所有生成准入同时要求新鲜的生成许可和新鲜的短期窗口分类。不能因为新的周字段到了，就顺便刷新旧短期字段的观测时间。短期 active 即便观测时间旧，也先阻挡发送并重新核对；active 的 reset_at 到期后不直接在准入函数中当作 inactive。

纯准入函数分别检查 `QuotaObservedAt`、短期分类观测时间 `FiveHour.ConfirmedAt`，以及周任务的 `WeeklyObservedAt`。`WeeklyConfirmed` 表示联合重置边界及可激活状态已核对，不表示发送前新窗口已经激活。

配置 `quota_max_age_before_send=0` 表示强制主动查询，并非核心接受零新鲜度。配置适配层拆成 `ForceObserveBeforeDispatch=true` 和正数 `EvidenceMaxAge`（首版内部阈值 30 秒）。每次操作必须取得本轮新分配查询序号、匹配账号代际的结果，再传入准入；不能复用旧缓存或把 0 单纯替换成 30 秒跳过查询。`DecideAdmission.QuotaMaxAge` 始终为正，若查询后的检查延迟使任一字段超过阈值则重新查询。

本地到期产生 `Intent`：账号、凭据代际、规则、稳定本地周期构成身份。`RandomizedDueAt` 创建时抽取一次，并与事件一起持久化。配置热更新、重启、候选重新排序、名额变动不重新抽签。随机延迟是最早准入时间，不承诺在窗口内一定发出。错过时直接进入当前条件检查；不能把新观测到达时间当作新的随机起点。

## 3. 周联合重置

“周重置同时重置 5 小时”是用户提供的账号行为假设，不当作所有上游账号的保证。周任务有最高政策优先级，但不会越过准确账号绑定、窗口证据、生成许可、正常请求占用和总并发。

本地周基线到期后建立周事件。到随机时间，读取周和短期的新鲜状态。只有观测确认联合重置，reducer 才能将旧短期基线和旧短期事件取代；周事件自身到期不授权直接清除正在生效的短期窗口。新正常请求已经启动短期窗口时，不发送。观测出现周重置但短期仍 active 时记录 `weekly_reset_conflict`，等待继续核对。

即使旧周期的 `expired` 数据晚到，也不能覆盖本地已确认且仍在未来的短期截止时间。只有同次响应的周与短期字段都通过新鲜度和序号检查、且确认本地周边界已过去，才允许联合重置替换该截止时间。曾收到 `unknown` 也不会清除这一稳定基线保护。

联合事件可以吸收对应旧短期事件，但“被新周期取代”和“本次请求已经验证完成”是不同状态。尚未到随机时间的普通或每日事件不自动取得此次生成的完成标记。短期验证完成而周证据缺失时只继续观测周，不再生成第二次。

## 4. 容量与政策准入

以普通规则的参与账号集合为容量范围。每个账号最多计一次；周任务关联账号若也参与普通规则，周预约与它启动的窗口同样计入容量。周专用且退出普通池的账号不增加普通容量。参与者过多并不意味目标限制能阻止真实用户自行启动更多窗口。

```text
limit = min(普通参与账号数, 可选max_accounts)
user_target = min(limit, ceil(近期去重用户数 * accounts_per_user))
target = min(limit, max(user_target, 当前到期每日任务最低容量))
A = 参与池内已确认可用窗口的账号集合
P = 参与池内准备发送/发送中/待验证账号集合 - A
missing = max(0, target - |A| - |P|)
```

MaxAccounts 不配置代表池容量上限；配置 0 表示不准备普通容量。计算前拒绝负数、NaN、无穷比例；先截断乘积再转整型，避免大值溢出。

`DecideAdmission` 输入的 `OrdinarySlotReserved` 必须是协调器本轮重新核对后保留的本账号预约。当已有预约计入 P 导致 missing=0 时，本账号仍能使用该预约；不能把自己计入 P 后又以“没有名额”拒绝自己。目标降低时，协调器先撤销尚未发出的多余普通预约，再计算准入；不能给已撤销预约继续传 true。

周事件到随机时间且联合重置确认后，不受用户人数、普通名额和普通允许时段限制。尚未到随机时间的周事件不能给同账号普通事件提供豁免。普通短期事件夜间只在近期用户数大于 0 且例外开关开启时执行；仅每日事件不能借用这一例外。每日事件表达池级准备目标，选择账号后才关联账号任务。

容量重算和预约建立必须在一个串行协调器内完成；纯函数结果不是全局锁。多 worker 同时计算相同 missing 再各自发送会超配。周预约即使把容量推到用户目标以上也可以执行，随后普通任务不再填补。

## 5. 观测顺序、凭据与查询边界

额度查询与执行结果通常会乱序到达。只比较 ReceivedAt 会让慢查询覆盖请求之后的新窗口。拟采用如下每字段接受栅栏：

1. query 开始前取得本地序号 `ReadStartedSeq`，并绑定账号代际。
2. 真实请求或唤醒请求完成时，由协调器分配新的接受序号；其有证据字段更新 `AcceptedSeq`。
3. query 返回时，每个字段分别检查：若该字段已接受序号比 query 启动序号新，则该字段丢弃，缺失字段不更新。
4. 未被拒绝的 query 字段在接受时再得到新序号；并行查询也不能反向覆盖已接受字段。
5. 明确的上游测量时间、周期关系和操作关联用于拒绝逻辑冲突；本地到达顺序不构成上游状态绝对真相。

长生成请求可能早于某个查询开始，但完成响应是较新的执行证据，因此不能对所有来源简单采用“启动序号小就全部丢弃”。`ObservationClass` 区分查询与执行响应；执行完成进入接受栅栏，查询用其启动栅栏比较。`ApplyObservation` 已实现该接受规则。协调器在开始查询前调用 `NextSequence`；每个接受字段也分配一个新序号。缺失字段不更新，旧代际响应整体丢弃。

账号重登、替换凭据或被删除之后，旧代际观测、任务、预约都不能应用到新绑定。Host 端应在精确发送时再次核对 generation。`Host.ObserveQuota` 是本项目适配器提供的行为，不代表官方存在 `host.quota.fetch`。

## 6. 状态转换、合并与发送意图

每账号代际只有一个合并任务；一个任务可以带多个持久化 Intent。只有成熟且 pending 的意图参与本轮优先级和 `CoveredEventIDs`；covered 集合在发送意图提交时冻结，新事件不追加进已发操作。

```text
pending/waiting → reserved → dispatch_intent → verifying
verifying → satisfied 或 awaiting_evidence
awaiting_evidence → 继续观测 或 satisfied
明确未发送 → waiting（原随机时间保留）
停用/凭据失效 → suspended
```

协调器的实际事务顺序：账号代际检查 → 新鲜额度及前台状态检查 → 串行名额/并发仲裁 → 预约和完整 dispatch_intent 一次 durable CAS 提交 → 调用 Host.SendExact → 持久化结果 → 验证证据并更新基线。

`Store.Commit` 的 CAS 和成功返回必须代表持久化完成，不能是异步写盘排队。写盘失败不调用 Host。当前 [本地存储](storage.md) 使用进程锁、原子替换和 fsync；CAS 或落盘失败会停止协调器，重新打开并核对实际状态后恢复，不自动重复发送。

正常请求与插件发送之间仍可能有竞态。本地锁只协调插件自身，不协调宿主路由；`ForegroundGuard` 能力要求宿主原子地确认该账号没有已满足任务的前台执行再放行精确发送。若宿主只能提供观测后调用而不能实现原子防护，必须显示此能力缺口，不能声称严格排除了重复激活请求。

## 7. 未知结果与容量预约

`dispatch_intent`、`verifying`、`awaiting_evidence` 都禁止重新生成。重启发现 dispatch_intent，即使进程可能在实际调用前崩溃，也先验证而非直接补发；本地写盘和远程请求不具备共同事务，不能承诺故障下恰好一次。

`SendDefinitelyNotSent` 是唯一默认允许重新排队的结果。HTTP 失败或明确 rejection 不自动等同于“未发送”；可能已有部分处理，先结合宿主送达证据与窗口核对。流内异常、超时、断流、无法确定失败位置归入 unknown。`SendCompleted` 仅表示完整业务流完成，仍需分别验证短期、周和每日容量。

防重复发送与预约占容量是两件事。等待证据期间暂时占 P，防止同轮无限补账号；若可信证据确认不可用，或超过 `execution.verification_capacity_hold`（默认 15 分钟），协调器可释放容量预约，让其他账号满足需求，但本账号仍保留 awaiting_evidence 和发送抑制。保留时间从发送完成或转为不确定时开始，并以 `Reservation.CapacityHoldUntil` 持久化；重新验证、热更新和重启不重新起算。超时释放 P 不能把任务转回可生成。预约复查期限与状态应在 UI 可见。

## 8. 用户统计能力与降级

主方案在经核对且支持认证 `caller_scope` 的 CPA 版本，于真实请求开始按该 scope 去重，并在 after 阶段结合 selected account 标识追踪占用。身份来自宿主认证，不相信客户端任意填写的 user ID。请求开始、结束事件需要可靠关联；插件自身 SendExact、额度查询和管理调用排除。

`ActivityEvent` 包含宿主稳定 `RequestID` 和明确 phase：`started`、`account_selected`、`completed` 或降级模式的 `completion_only`。同一请求重试的多次选账号事件更新同一绑定，并释放旧账号的占用；结束事件根据保存的映射幂等释放，不要求完成元数据重新提供完整身份。不同用户同时使用同一账号和同一用户的并发请求都以请求 ID 集合计数，而非直接把每个回调加一。

适配器必须核对具体版本并声明 `ActivityIdentityAtStart` 与 `ActivityIdentityAtCompletion`。缺少开始身份的版本只能按完成请求的认证身份统计最近 30 分钟；这会漏掉尚未完成的第一个长请求，不能假称持续计入长请求用户。只有完成事件可用时，UI 明确说明统计口径。认证 API key 原文不得写盘，用本地带密钥摘要；共享 key 的多人仍算一个身份。

用户数在最后活动后 30 分钟自动下降；无新消息也需通过到期计时器重新计算。真正支持开始/结束身份时，正在进行的请求持续计入；必须处理断流结束和服务重启，不得把遗漏 finish 的活动永久留在人数中。

## 9. 相对原逻辑设计的具体修正

- “最新额度”改为每字段新鲜度和接受栅栏，防止新周字段掩盖旧短期字段。
- “已有预约后重算名额”明确保留自身预约，否则 P 会把自己的机会扣掉。
- 周联合确认仅使被证据取代的旧短期周期失效，不能清掉有效的新短期窗口。
- unknown 发送的容量预约可按明确规则释放，但发送抑制独立保留。
- 前台 busy 的单次读取不提供原子性；需要宿主防护能力，缺失时明确限制。
- 开始用户身份按 CPA 版本能力探测；没有能力时按完成统计，并标记长请求限制。

首版限定一个账号池一个执行实例。若多主机共享账号，必须有共享执行权、统一状态与用户来源；当前 CAS 端口是本地逻辑边界，不自动提供分布式租约。

## 10. 验证与下一步

核心 reducer 的具体调用顺序：`ReconcileAccounts` 同步宿主清单，协调器覆盖配置开关；`GenerateResetIntents` 接受独立五小时/周启用开关和各自的 `DelayRange`。`ApplyActivity` 按 RequestID 幂等处理开始、重新绑定账号和结束，未知结束不会新增用户；仅完成统计必须显式使用 `completion_only`。`ExpireActivityRequests` 以宿主请求超时上限清理遗漏结束，并保留可配置重放期限的完成墓碑。

派发前调用 `MarkDispatch`，其仅冻结成熟且 pending 的 covered 事件；随后由 Store 提交持久化状态，才能调用宿主。`ApplySendResult` 仅在明确 `definitely_not_sent` 时恢复等待；其他结果保持查询验证，预约容量期限由协调器传入持久状态，不内置固定时长。`ReleaseExpiredReservations` 仅释放名额；`RecoverAfterRestart` 将遗留发送意图转为等待证据，不重新发送。真正的新活跃窗口让成熟周期标记 satisfied，让尚未到随机时间的旧周期标记 superseded，随后更新本地稳定基线。

`ConfirmedAt` 始终表示字段分类的新鲜度。核心不会把它当作上游激活时间，`WindowBaseline.LastConfirmedActivation` 因缺少独立激活证据保持未设置。

骨架测试覆盖容量目标截断、重叠预约去重、日程最低容量、夜间短期活动例外、周豁免、周确认冲突、成熟意图合并、补发、自身预约、有效窗口和未知发送抑制。测试不模拟真实 CPA 或上游额度机制。

```sh
GOCACHE=/tmp/codex-window-refresh-go-cache go test ./internal/core
GOCACHE=/tmp/codex-window-refresh-go-cache go vet ./internal/core
```
