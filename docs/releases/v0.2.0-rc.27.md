# v0.2.0-rc.27 客户端提供商输入与记忆

修复客户端默认使用 cpa 时，已有 Codex 配置只定义 cliproxyapi 等其他提供商而导致 `model_providers.cpa: provider name must not be empty` 的启动错误。现在直接运行 cwr-codex 会优先使用已记住的提供商 ID，没有记忆时默认 cliproxyapi，不读取或修改 Codex 配置，也不强制切换实际提供商。

Codex 报当前 ID 对应的 `provider name must not be empty` 错误后，交互终端提示用户输入已配置的提供商 ID。输入格式检查通过后，原子保存到 `$XDG_CONFIG_HOME/cwr/client.json`，默认 `~/.config/cwr/client.json`，随后重试启动 Codex。下次直接运行即可使用已记住的 ID；旧记忆失效时可再次修正。回车、Ctrl+C 或输入结束可取消，其他 Codex 错误保留原输出和退出状态。非交互运行不会等待输入，提示使用 --provider；显式 --provider 仍只覆盖本次启动，正常启动不改变已有记忆。

启动器保留 Codex 的标准输入和输出终端，实时转发诊断，仅在内存保留最多 64 KiB 的近期标准错误用于识别这类启动失败，并转发终止信号。目录标识、请求头、项目映射及服务端首选账号规则保持兼容。客户端安装器固定到 rc.27 标签源码并校验新脚本 SHA-256，保留已记住的提供商、目录映射及 Codex 配置；仍支持 Linux/macOS、Python 3.10+、自定义目录和离线安装。

**这次客户端修复可单独更新客户端，现有 rc.26 服务端无需升级或重启 CPA。** 配套后台更新为 rc.27，仅同步网页使用提示；原生接入层保持 rc.26，数据库保持 schema 11。从 rc.26 同时更新后台时，安装器只有在接入层文件完全一致后才允许仅重启后台；从 rc.25 或更早版本升级仍需同时更新接入层、显式 --restart，并遵循 schema 11 的一致备份和降级要求。

验证包含默认 ID、模拟及真实 Codex 的报错/输入/记忆/重试、再次无参数启动、取消、非交互与非提供商错误、单次覆盖、记忆文件异常处理、安装更新保留偏好，以及真实 Codex 伪终端交互。发布流程运行 Go 测试、vet、竞态、原生桥联调、脚本测试和完整 Chromium 回归，并在 amd64/arm64 构建及验证公开安装包的安装更新和回滚；使用临时配置和模拟宿主，未调用真实模型或重置卡。

客户端安装与使用见[项目与账号](../account-scheduling.md#项目与账号)，服务端更新见[V2 安装与更新](../backend-v2-install.md)。
