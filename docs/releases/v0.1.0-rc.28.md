# v0.1.0-rc.28 内存开销与热重载释放修复

修复已在本地确认的状态复制开销和旧实例保留问题。真实部署报告的“内存持续上涨、被系统杀死后反复重启”尚缺内存曲线、状态大小和 OOM 日志，不能据此认定所有原因均已解决。

- 热重载暂停成功后释放旧调度器及账号状态、请求记录、历史和发布快照，不让 CPA 保留的旧库继续引用这些对象；归还闲置 Go 堆内存。回滚重新获取状态锁并从已提交文件重建，暂停超时继续保留所有权，不提前释放。
- 快照直接复制可变容器，保留读者隔离，共享不可变字符串与时间位置；不再用 JSON 编解码复制全部历史消息。
- 保存前两次文件复核改为流式 SHA-256 校验，使用与已验证内容绑定的修订号，不再两次构建完整状态对象。仍检查文件身份、权限、进程锁、大小、外部修改及持久化提交结果。
- 启动严格解析文件一次；首次 Load 重新核对全部文件内容后转移该状态的所有权，后续 Load 仍独立读取。空闲变更检测只保留摘要，不将完整历史 JSON 留在网络等待期间。
- 原生诊断不再为读取几个字段复制全部状态；清除历史数组中已裁剪消息的残余引用。

在本地独立进程中，对 100 个账号、1 万条已完成请求和 1 万条各 1 KiB 消息的模拟历史连续发布 25 次快照：单次累计分配从约 64.8 MB 降至 5.4 MB；该测试进程的峰值 RSS 从约 246 MiB 降至 66 MiB。另一组同规模请求与历史的文件保存基准，单次累计分配从约 226 MB 降至 39.5 MB。累计分配量不同于常驻内存，这些数值不是实际 CPA 进程的内存承诺。

验证包括深复制隔离、空闲不重复提交、历史裁剪释放、首次读取的所有权转移、外部编辑拒绝，以及完整 Go 测试、竞态检查、原生 ABI 热重载/回滚/状态锁交接、安装器与网页检查。原生测试不连接上游、不发送模型请求；真实生产 OOM 仍需部署后观察。

如果 CPA 正在 OOM 重启循环，先停止其实际服务，在 CPA 主配置中将 `plugins.configs.codex-window-refresh.enabled` 设为 `false` 后恢复服务。保留 `window-refresh-state/state.json`，其中包含已发送请求的防重复发送记录。

更新时建议显式重启一次，清理旧版无法自行释放的驻留对象；默认热重载行为不变。已确认 CPA 位于 `/root/cliproxyapi` 时：

```sh
curl -fSL https://raw.githubusercontent.com/JayConstruct/codex-window-refresh/main/scripts/install.sh -o /tmp/codex-window-refresh-install.sh && sudo bash /tmp/codex-window-refresh-install.sh --cpa-dir /root/cliproxyapi --version v0.1.0-rc.28 --restart
```

升级保留已有配置、窗口、原定唤醒时刻及发送抑制状态，不需要删除或重置状态文件。若重启后仍上涨，请提供版本、服务器内存、账号数量、状态文件大小和内核 OOM 日志，避免贴出策略、令牌或完整状态内容。
