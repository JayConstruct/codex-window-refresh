# 项目账号调度、插件会话粘性与官方重置卡

V2 预发布版本 v0.2.0-rc.21 增加业务选号和赠送重置卡管理。它们分别有开关，升级默认关闭；旧查询、唤醒规则保留。需要同时更新原生桥和独立后台并重启 CPA，数据库迁移到 schema 10。升级前备份一致数据库；不能把 schema 10 直接交给 rc.20 或更早后台。

rc.23 增加下述插件会话粘性接管。数据库保持 schema 10，旧调度配置自动补充子代理继承开启、仅额度或认证失败时重绑的默认值。已有调度总开关保持不变；加载新粘性管理必须同时更新后台、原生桥并重启 CPA。

## 项目与账号

rc.26 起支持客户端自动目录标识，无需维护 `projects.json`。rc.27 客户端默认使用已记住的 ID 或 `cliproxyapi`，提供商启动报错时可输入实际 ID 并保存；已有 rc.26 服务端可以继续使用。Linux/macOS 在运行 Codex 的电脑安装或更新客户端（Python 3.10+、curl，无需 sudo）：

```sh
curl -fSL -H 'Cache-Control: no-cache' https://raw.githubusercontent.com/JayConstruct/codex-window-refresh/main/scripts/install-client.sh -o /tmp/cwr-client-install.sh && bash /tmp/cwr-client-install.sh
```

默认安装到 `~/.local/bin`。检测到 `~/.codeman/app` 时，自动为 Codeman 的 Codex 模式配置客户端启动入口。**重启 Codeman 服务后**，新建或恢复的 Codex 会话自动按工作目录携带项目标识，模型、推理强度、动画及恢复会话参数继续由 Codeman 传入。

Codeman 使用默认用户服务 `codeman-web.service` 时，一条命令安装本版客户端、配置入口并重启 Codeman：

```sh
curl -fSL --retry 3 https://raw.githubusercontent.com/JayConstruct/codex-window-refresh/v0.2.0-rc.31/scripts/install-client.sh -o /tmp/cwr-client-install.sh && bash /tmp/cwr-client-install.sh --codeman-dir "$HOME/.codeman" && systemctl --user restart codeman-web.service
```

使用其他启动方式时，仅运行安装器，再通过原来的管理方式重启 Codeman。

Codeman 入口使用其 CLI 注册表 `~/.codeman/clis.json`，通过已安装的 `app/dist/config/cli-registry` 模块读取并校验当前启动模板；保留其他 CLI、Codex 开关及现有参数。首次修改已有注册表时保存 `clis.json.cwr-backup`，注册表及备份使用 `0600` 权限。重复安装更新入口路径，不重复添加启动参数。不替换原始 Codex 程序，不修改 shell 或 Codex 配置。无效注册表、已有自定义 Codex 启动命令或缺少注册表模块时，原注册表保持不变并提示原因。

仍提供 `cwr-codex` 命令及兼容原路径的 `cwr-codex.py`，终端可直接使用；未加入 PATH 时可运行 `~/.local/bin/cwr-codex`。自定义安装目录使用 `--bin-dir /absolute/path`；Codeman 入口记录客户端绝对路径，不要求安装目录已在 Codeman 的 PATH 中。`--codeman-dir /path/to/.codeman` 可指定包含 `app` 的 Codeman 数据目录，`--no-codeman` 仅安装客户端。已有客户端也可执行 `cwr-codex --setup-codeman /path/to/.codeman` 单独配置。配置 Codeman 入口另需 Node.js 及支持 CLI 注册表的 Codeman；普通客户端仍只需 Python。重新下载并运行同一安装命令即可更新，下载或校验失败不会覆盖旧脚本。已有 Codex 配置和目录映射保留。离线安装可在完整解压的发行包中运行 `bash install-client.sh`，无需 curl。

1. 在 Codeman 中选择项目目录，以 Codex 模式启动会话，再发送一次正常请求；终端也可进入项目目录执行 `cwr-codex`。新版脚本不读取 Codex 配置，默认使用已记住的提供商 ID，没有记忆时使用 `cliproxyapi`。若 Codex 报该提供商定义缺失或名称为空，则在会话终端按提示输入实际 ID，保存到客户端设置后自动重试；下次无需再填。
2. 在面板“账号调度与重置卡”找到“客户端最近出现的项目”。客户端上报目录名和 `dir-` 开头的稳定标识；点击“匹配账号”，可填写便于辨认的项目名称，再从 CPA 账号清单选择首选账号。
3. 开启业务账号调度并“保存并应用全部设置”。账号偏好保存在服务端，后续新会话按该项目选择账号，客户端无需重新下载文件。已有会话绑定继续沿用原账号。

标识使用 SHA-256，输入为固定版本前缀、客户端操作系统和解析符号链接后的绝对项目路径。优先使用最近的 Git 项目根目录（包括 worktree），否则使用启动目录；同一 Git 项目的子目录使用同一标识。路径移动后标识会改变；相同操作系统下的相同绝对路径会得到相同标识，即使来自不同电脑。需要将这些目录分别配置时，可用原有 `--project` 手动指定不同项目。

客户端通过 `X-CWR-Project` 传入标识，并用 `X-CWR-Project-Name` 附带百分号编码的目录名（最多 64 个 UTF-8 字节），不发送完整路径。原生桥只从已认证、候选全部属于 Codex 的正常业务选号中记录自动目录标识，不读取正文。观察使用有界内存事件队列，不在选号路径访问数据库或网络；同一缓存项目的重复观察合并一分钟。后台持久保存最近最多 1024 个标识、目录名及首次/最近出现时间，面板支持搜索及每页十条。观察不会创建项目偏好、修改设置 revision、产生模型调用或制造活动会话；关闭业务调度时仍可记录项目，但不介入选号。

**自动发现需要一并更新到 rc.26 客户端、独立后台和原生接入层，并重启 CPA。** 数据库从 schema 10 升至 11，只增加项目观察记录，保留账号、规则和兑换防重记录；schema 11 不能直接交给 rc.25 或更早的后台。rc.25 安装包使用旧方式，不包含自动发现。

兼容已有 `projects.json` 时，可继续在“项目目录与账号匹配”中维护目录和账号：

1. 新增项目并填写项目标识、运行 Codex 的电脑上的绝对目录；同一项目可填写多个目录。也可导入客户端已有的 `projects.json`，同名项目的首选账号会保留，目录冲突时整个导入不应用。
2. 点击项目的“匹配账号”，在 CPA 已同步的 Codex 账号清单中点选首选账号。支持账号 ID 或完整本地别称搜索、状态筛选和独立分页；显示已有的五小时、周额度及观测时间，查看和刷新清单不查询上游、不发送模型。
3. 保存全部设置，再点击“下载目录映射”。将文件放到客户端的 `~/.config/cwr/projects.json`，通过下述启动器运行 Codex，目录才会转换为调度请求中的项目标识。

目录清单来自手动登记或导入客户端文件，后台不读取客户端文件系统。每个项目最多 16 个目录、1000 个首选账号，总计最多 128 个项目，完整设置不超过 256 KB。同一目录不能重复分配，嵌套目录允许；启动器在客户端解析符号链接并使用最长路径匹配。混合平台清单中的其他操作系统绝对路径会被启动器跳过。

目录作为可选的管理元数据与项目偏好一起按 revision 保存，旧配置无需修改；项目名称同样是管理元数据。发布给接入层的项目偏好只包含项目标识与首选账号，不包含客户端目录或显示名称。rc.25 起，完整支持大于 6 KB 的调度设置需要同时更新到 rc.25 原生接入层，并显式重启 CPA。

高级文本编辑仍支持项目首选账号，每行例如：

```text
project-a = account-1, account-2
project-b = account-3
```

文本编辑时，同名项目保留已登记目录；删除或重命名项目会移除对应的目录映射。目录与项目账号只在保存后应用，未保存、配置冲突或保存结果待核实时不能下载新映射。

这些是首次分配时的软偏好：首选账号不可用或达到并发上限时，可以回退其他可用候选。项目标识不授予账号访问权限。CPA 原有模型支持、禁用、冷却和显式指定账号继续生效；新会话优先最高可用优先级，已有绑定可以继续使用较低优先级账号。插件声明 `scheduler_across_priorities` 以接收这些候选。已有其他选号插件时，应避免同时启用多个选号插件，宿主只选择一个活动 Scheduler。

客户端使用仓库或安装包内的 Python 启动器：

```sh
python3 scripts/cwr-codex.py --project project-a --directory /work/project-a
```

通过脚本或已配置的 Codeman Codex 入口启动时，启动器为本次 Codex 进程传入 `X-CWR-Project` 请求头设置；终端直接运行原始 `codex` 时，不额外添加项目头。启动器不读取或检测 Codex 配置及 profile，普通客户端使用 Python 3.10+ 即可，无需安装 `tomli`。

新版默认使用 `cliproxyapi`，交互输入的 ID 保存到 `$XDG_CONFIG_HOME/cwr/client.json`（未指定 XDG_CONFIG_HOME 时为 `~/.config/cwr/client.json`）。脚本只捕获当前提供商对应的 `provider name must not be empty` 启动错误；回车、Ctrl+C 或输入结束可取消，HTTP、认证或其他错误照常退出。非交互运行时不等待输入，会提示通过 `--provider` 指定 ID。客户端安装或更新保留这个记忆文件。

`--provider` 可单次覆盖已记住的 ID，例如 `--provider my_proxy`；成功启动不会把单次覆盖写成默认值。启动器将头部设置写入 `model_providers.<ID>.http_headers.X-CWR-Project` 启动参数，不替换 `model_provider`，不修改 Codex 配置文件或服务器调度总开关。提供商 ID 及其 CPA 地址由用户配置，启动器不自动判断或切换。Codex 的 profile 和其他命令行参数照常透传。

这些是[当前客户端启动器](../../scripts/cwr-codex.py)的用法，旧安装器需要更新后才会配置 Codeman 入口。rc.25 安装包仍包含提供商检测逻辑。当前脚本的显式 `--project` 和原有目录映射可配合旧后台使用，自动发现需要后台和接入层至少为 rc.26。rc.27 的提供商交互修复可单独更新客户端。启动器不保存密钥、不改写请求正文，请求头仅通过本次启动参数传入。

需要沿用自定义项目标识或将多个目录合并到同一项目时，可选创建 `~/.config/cwr/projects.json`：

```json
{"projects":[
  {"directory":"/work/project-a","project":"project-a"},
  {"directory":"/work/project-b","project":"project-b"}
]}
```

然后在 Codeman 中使用对应目录启动 Codex，或在终端执行 `python3 /path/to/cwr-codex.py`。新版会使用已记住的提供商 ID 或默认 `cliproxyapi`。手动 `--project` 优先，其次是现有目录映射的最长路径匹配，最后自动生成目录标识；默认映射文件不存在时直接使用自动标识，不创建文件。`--map` 可指定另一份映射，显式指定的文件不存在、内容损坏或映射重复时会报错。希望已有目录改用自动标识时，移除对应映射即可。使用 `cwr-codex` 时，Codex 参数放在 `--` 后，例如 `cwr-codex -- exec "检查测试结果"`。启动目录可用原生 `-C`/`--cd` 指定，也可使用启动器的 `--directory`；项目标识按最终目录计算。终端直接执行 `codex` 可普通启动。

## 额度分配

先保留当前会话绑定，再考虑父会话继承；确实需要新账号时，按宿主最高可用优先级 → 项目首选组 → 新鲜有效额度 → 临近重置/重置卡到期 → 当前并发占用选择，完全相同时轮换。项目偏好或重置时间变化不会拆掉已有绑定。显式指定账号只影响本次请求，不建立或改写会话绑定。

只有可信且新鲜的五小时、周额度及 permission 证据获得额度排序优先；新鲜耗尽证据排除账号，额度未知或过期仍以 CPA 提供的可用候选为准。账号身份与额度新鲜度分开保存，过期额度不会拆掉有效绑定。原生桥只读取内存，每次选号不访问数据库、不主动查询上游。后台每两秒更新快照；十秒未续期时停止使用旧额度排序，继续由插件基于内存绑定、宿主可用候选和本地并发选号，已知兑换保护继续保留。额度证据默认最长有效五分钟，仍需开启合适的自动额度查询以持续获得优先调度。

并发保护包含按宿主 `selection_id` 建立的短暂预约、账号选定后的活动请求以及完成释放。同一次选号重试不会重复预约。预约十五秒过期，缺失完成的活动记录最长保留十分钟；总共最多 4096 项在途记录，达到上限拒绝新选号，不覆盖活动记录。它是基于生命周期观测的本地保护，不提供跨进程、跨插件的原子执行租约。绑定账号繁忙或正在兑换时返回 `scheduler_busy`，不为了并发临时换掉该绑定。

## 插件会话粘性

在“账号调度与重置卡”开启业务账号调度后，插件统一管理主会话、子代理、分支和压缩后会话的账号绑定；这些 Codex 请求由插件选号，不依赖 CPA 内置粘性缓存。关闭调度则不再由插件选号。仅处理候选均属于 Codex 的请求，混合提供商及其他提供商继续交给 CPA；插件自己的后台模型操作保持精确账号执行。

接管实现以 CPA v8.0.47 的插件契约为基线，使用跨优先级候选、规范会话/父会话元数据、每次选号 ID 和执行结果通知；旧宿主需先确认这些接口是否齐备。CPA 原有粘性设置无需改写，插件开启时使用本页的绑定策略。

绑定按已认证 `caller_scope`、项目、提供商、请求模型和规范会话 ID 隔离。优先使用 CPA 的 `canonical_session_id`、`parent_session_id`，兼容常用会话和父线程请求头，头名称不区分大小写。不读取提示词或正文来猜父子关系；客户端或宿主未提供父标识时，无法自动继承。缺失调用者、模型或会话标识时正常选号，但不建立共享绑定。

“子代理继承父会话账号”默认开启。新子会话、分支及压缩后新会话首先尝试父会话相同模型的绑定；父会话跨模型的现存绑定一致时，也可继承到宿主确认支持的另一模型。继承后创建子会话自己的记录，后续子会话重选不改写父记录；嵌套子代理同样处理。关闭开关只阻止新的继承，已建立的子会话绑定继续生效。

“失败后的重绑定条件”有两种：

- 默认 `quota`：执行以 401、403、429 失败时解除对应绑定，短暂避开失败账号再选；临时网络、408、5xx 故障保留原绑定。原账号不在本次宿主候选中时允许本次回退，之后可回到原账号。
- `any`：除额度和认证失败外，临时网络、408、5xx 失败也解除绑定，原账号不在本次候选中时重新绑定可用账号。客户端取消、拦截拒绝和 400/404/422 请求错误均不触发该策略。

账号被删除、禁用、凭据绑定替换或取得新鲜耗尽证据时，旧绑定失效。通过 CPA 的 `usage.handle` 读取单次上游执行的选号 ID、账号与失败状态码，即使宿主内部换号后最终成功，也能处理先前失败；逻辑请求完成事件补充取消与最终失败状态。保留有限期的选号归属，旧账号上的迟到失败不能清除后来建立的新绑定。通知不读取或保存客户端 API key、失败正文、提示词和 token 用量。显式账号指定始终遵从 CPA 的候选过滤，并保留原会话绑定。

“会话空闲失效时间”默认 1800 秒，实际使用会续期；最多保存 4096 个绑定，满时淘汰最早失效的记录。绑定只在原生桥内存中，CPA 重启、插件卸载或切换调度开关会清空，独立后台重启不清空。旧 CPA 内置缓存不迁入，接管后的首次请求重新建立插件绑定。

## 官方赠送重置卡

rc.22 起，正常账号额度查询会保留上游 `/wham/usage` 中可选的 `rate_limit_reset_credits.available_count`，页面可直接显示卡片数量，不增加请求，也不要求安装 Codex CLI。缺失字段表示未知，不能推断为零。数量摘要不含卡片 ID 和到期时间；它们由独立详情查询补充。新数量与旧详情数量不一致时，不展示旧卡片列表；摘要更新不会刷新详情的观测时间。

卡片详情查询和兑换需要可执行的 Codex CLI，且必须支持官方文档中的 `account/rateLimits/read`、`rateLimitResetCredit/consume` 和外部 ChatGPT token 登录。可通过后台参数 `--codex-binary /absolute/path/to/codex` 指定。旧版、不支持该协议或未安装时展示诊断，不调用网页内部端点。

每次账号操作使用独立临时 CODEX_HOME、内存凭据存储和 stdio RPC，凭据仅在内存及匿名管道传输，不作为命令参数、日志或数据库内容。适配器不开模型会话。账号显式代理/direct 设置会被继承；账号没有代理覆盖时，重置卡适配器使用 `--reset-proxy`，未指定则继承后台进程代理环境。它使用 Codex 进程网络栈，**不会自动读取 CPA 全局代理**；需要代理的部署应为该后台单独配置。既有额度查询仍通过原有 CPA HTTP 桥继承宿主全局代理。

面板分别开启“后台查询重置卡详情”和“到期前自动使用”。默认每账号十五分钟查询一次，接近已知到期时间时提前补读；所有卡片请求串行执行，大账号池实际轮询周期还受账号数和响应耗时影响。服务缺少到期时间或仅返回卡片数量时，保留未知状态，不猜测日期、不自动兑换。

默认关注一天内到期的卡，优先最早到期的一张；五小时或周窗口已用达到 80% 时可以兑换，最后三十分钟内则只要存在有用的已使用窗口就尝试。自然重置距离不足五分钟的窗口不作为兑换理由。执行前先查询额度、核实账号绑定、检查配置和其他后台发送占用。不能重置的窗口由官方返回 `nothingToReset`，不会创建模型请求来人为消耗额度。

兑换前持久保存操作 ID，并作为 `idempotencyKey`；超时、响应丢失、重启后复用同一 ID 和同一张卡。明确返回 `reset` 或 `alreadyRedeemed` 后只做额度和卡片补读，不再次兑换；读到五小时和周额度均可用后，清除 CPA 对该账号的本地路由冷却并请求重新同步；已因额度耗尽而暂不可用的账号仍可核实和兑换，手动禁用始终阻止兑换。完成后显示“已兑换并查询额度”，不根据兑换回执构造新的倒计时。`noCredit`、`nothingToReset` 记录为本次未兑换。结果未知保留账号后台发送保护；关闭自动兑换后不会继续变更操作，已确认兑换的只读核实可以继续。

管理 API：`GET/POST /v0/management/codex-window-refresh/v2/scheduling` 使用 revision 比较保存；`GET .../reset-cards` 读取卡片与最近兑换记录。它们通过 CPA 管理认证，读取设置和打开页面不会查询上游或兑换。
