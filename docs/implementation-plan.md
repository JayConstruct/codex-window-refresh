# 插件实现阶段与验收边界

## 当前阶段

当前目录不是已有 CPA 项目的副本，而是新插件工作区。插件 ID 采用 `codex-window-refresh`，避免与现有的 `codex-quota-scheduler` 混淆。

当前已实现规则核心、后台协调器、严格配置解析、原子文件存储、CPA 指定账号执行与额度管理桥，以及 Linux 原生注册入口。提供已认证管理 API、中文网页面板和带内容版本检查的规则保存。原生动态库已通过 C 假宿主加载测试；尚未在真实宿主和生产账号上联调。以下保留分阶段设计，实际可用接口以 [插件说明](plugin.md) 为准。

## 包结构

```text
internal/core/       纯领域类型、容量计算、准入决策、宿主/存储接口
internal/runtime/    待实现：单一状态仲裁器、定时器、事件收集、发送/验证工作队列
internal/storage/    待实现：原子持久化、版本检查、进程排他锁、迁移
internal/cpa/        待实现：版本化 SDK/ABI 适配、原生回调、精确账号执行
internal/quota/      待实现：额度查询及响应/流内额度归一化
internal/management/ 待实现：带版本的配置变更、状态和日志接口
cmd/plugin/         待实现：宿主加载入口，注册能力及生命周期
docs/               规则、接口、配置、实现设计
```

不存在的目录表示规划，不代表已有可运行代码。各适配器向 core 提供可信领域事件，不把 SDK 类型直接扩散到调度核心。

## 阶段一：纯核心规则

完成窗口证据、账号凭据代际、事件去重、任务合并、随机时间持久化语义和状态机。采用可注入时钟及随机源，在固定时间输入下检验行为。

验收：有效窗口不发送；周任务豁免人数与夜间但不豁免可信额度和重复发送抑制；已预约任务不会被自己的预约挤出名额；容量目标按不重叠账号集合扣减；过时观测不能覆盖新状态。请求活动按稳定 RequestID 和生命周期阶段关联，重试换账号不重复计数。配置新鲜度为 0 时强制本轮查询，核心仍逐字段使用正数证据年龄阈值。

核心 reducer 与运行时已覆盖该阶段的主要规则；当前网络操作串行执行，详见 [运行时](runtime.md)。

## 阶段二：存储和运行时

单一仲裁器负责用户数、容量预约与账号队列，网络工作线程只能提交结果事件，不能各自修改目标或抢占重复名额。保存发送意图成功后才能调宿主。

第一版使用本地原子文件存储和进程排他锁；同一账号池只运行一个执行实例。配置文件、状态文件和执行日志分开，不保存原始凭据。多主机共享账号需要后续共享租约。

验收：崩溃恢复只验证未完成发送；随机时间不会重抽；补发不回放全部历史日历事件；额度不确定时只查询不继续生成；用户统计即使没有新请求也会随时间过期。验证容量预约默认保留 15 分钟，期限持久化；释放容量后仍保留原操作发送抑制。

## 阶段三：CPA 与额度适配

使用 [接口核对文档](cpa-integration.md) 中固定的官方提交作为适配基线。宿主注册所需能力，并验证精确账号模型执行、额度查询和业务用量来源。

主方案使用已核对版本提供的认证 `caller_scope` 在请求开始时统计近期去重身份，通过请求完成事件释放活跃记录；完成用量作为补充。管理页面显示实际统计口径。旧版本缺少该字段时，降级为已完成请求身份统计，禁用无法可信获得的长请求持续活跃统计。生命周期观测还需验证异常断开和漏失完成事件后的清理策略。

自发请求不依赖被宿主跳过的自身观察回调更新状态，而由执行结果路径明确提交额度观测和验证事件。额度查询不是不存在的 `host.quota.fetch` RPC，需要单独适配实际接口。

验收：两账号宿主中，A 的任务只消耗 A；用户真实请求改变窗口后取消待唤醒任务；插件请求不增加活跃用户数；账号级代理和凭据更新沿用宿主行为；HTTP 成功但流内错误不认定为生成完成。

## 阶段四：管理界面与发布

按 [管理方案](config-management.md) 实现配置变更、账号状态、身份口径、容量计数和合并日志。配置更新检查修订号，重新评估尚未发送的任务，并保留已经抽取的随机时间。

验收：每个等待任务能解释原因和下次检查时间；配置被热更新后读回的实际状态与页面一致；无法取得用户身份时明确关闭人数模式或提示缺少能力，不静默伪造统计。

发布前才增加 CGO 动态库构建、明确支持的宿主版本、安装包、插件商店清单和校验文件。真实宿主加载及上述双账号验证通过后，才标记可安装。

## 规则边界

- 固定时间默认是池级最低可用容量，而非给每个账号发送一次。
- 普通夜间例外由近期用户人数触发；周任务在人数为零时仍可执行。
- 周优先用于已到时且可执行的任务。仍在随机等待或失败退避的周任务不阻塞其他普通任务。
- 插件不能控制普通业务路由到哪些账号，人数目标只限制主动唤醒，不能限制全部真实请求开启的窗口总数。
- 准入与真实业务请求之间仍可能发生竞态。自身单实例锁只能避免插件重复发送；若要求宿主业务与插件严格互斥，需验证或扩展宿主的共享执行锁能力。
- 无法通过本地记录和 HTTP 请求做到任意崩溃下恰好一次，采用持久化发送意图与不确定结果抑制。

## 本次设计验证

`make check` 检查测试与静态分析，`make race` 检查并发，`make native-smoke` 构建动态库并由 C 假宿主验证 ABI/schema、缓冲区与生命周期。本地加载测试不等于真实宿主验收。当前没有请求生产账号或部署插件。
