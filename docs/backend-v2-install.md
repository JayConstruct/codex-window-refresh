# v2 预发布安装与更新

适用于 Debian 12/13、amd64/arm64、CPA ABI 1/schema 6。CPA 与后台使用相同 UID，通过私有 Unix socket 通信。v2 提供网页、额度查询、持久任务、活动及正常业务额度观测。已发布 rc.5 支持自动额度查询及随机延迟，不包含模型唤醒、短句生成和自动模型规则；各包能力以对应发布说明为准。选择 v2 会停止 v1 功能，部署成功后清除 v1 策略、状态、环境文件、旧版本与备份；后续更新保留 v2 数据。

rc.6 新增可折叠侧栏、总览查询开关直接保存、模型与提示词持久配置及手动短句候选生成；生成需要显式选择账号和模型并确认消耗额度，不随安装验收、配置保存或额度查询自动执行。自动唤醒仍未实现。数据库迁移到 schema 5，并依赖新版接入层注册模型配置/生成管理路由和有界模型流接口，部署时须同时替换两部分并显式 `--restart`。

rc.7 支持反重力账号生成、独立生成账号目录及提供方协商，并将数据库迁移到 schema 6。rc.6 仍仅支持 Codex。升级需要后台与接入层同时更新并显式 `--restart`，不导入反重力账号到额度查询池，也不会自动调用模型或切换提供方。

rc.8 支持可编辑候选生成提示词及 Codex 模型唤醒，数据库由 schema 6/7 迁移到 schema 8；rc.7 仍为 schema 6，不包含这些功能。新接入层需声明 `wake_supported` 并注册唤醒设置与任务管理路由，因此须同时更新后台与接入层并显式重启 CPA，不能只替换网页或后台。仅保存模型/提示词不会发送模型请求；保存并开启自动唤醒规则后，后台可因后续额度观测创建发送任务，与网页是否打开无关。反重力仍仅用于候选生成。

rc.9 修复编辑焦点、完整窗口倒计时，增加按账号读取模型目录、Codex 风格提示词草稿及账号状态显示/筛选。数据库保持 schema 8，原生接入层源码和版本保持 rc.8；安装器按真实文件校验和判断是否需要重启 CPA，不仅比较版本号。从 rc.8 更新时，只有接入层文件一致才可省略 `--restart`；首次切换、旧接入层或文件变化仍须显式 `--restart`。详见 [rc.9 发布说明](releases/v0.2.0-rc.9.md)。

rc.10 保留候选、账号及历史控件的焦点和详情展开状态，修复轮询取消确认、无关历史读取禁用输入及分页读取竞争。数据库仍为 schema 8、原生接入层仍为 rc.8；从 rc.9 更新时，安装器确认接入层文件完全一致后可仅重启后台。详见 [rc.10 发布说明](releases/v0.2.0-rc.10.md)。

首次升级 rc.8 时先保持自动唤醒及五小时、周、每日规则关闭，核对实际模型、时区与允许时段，再显式手动唤醒一个测试账号。手动操作会先只读查额度和活动保护，可能跳过或阻塞，不保证一定发送；若发送则可能消耗模型额度。模型完成与窗口核实分开显示，结果未知不得换新键重复发送。确认行为后再按需保存开启自动规则。自动规则默认关闭并不覆盖旧版中用户已经明确保存的设置。

升级前须另存一致备份，范围包括查询任务、模型配置、候选任务和唤醒发送防重记录；停服务或使用 SQLite 在线备份，不单独复制活动 WAL 数据库主文件。升级不能清空未知发送记录来恢复可发送状态。安装包、迁移和验证范围见 [rc.14 发布说明](releases/v0.2.0-rc.14.md)。

旧后台不能直接打开迁移后的新库，回退必须停服务并恢复升级前一致的数据库备份，不能仅替换旧二进制。安装器激活失败时会使用临时一致备份恢复，但成功后会清理该副本；需要日后手动降级时，升级前须另行保存停机或 SQLite 在线一致备份。

rc.11 将操作反馈统一到全局 toast，正常轮询和草稿输入不刷屏，错误及未知结果警告可手动收起，发送保护不变。独立下载入口重新获取安装器，不复用旧副本，并显示实际后台及接入层版本。数据库与接入层版本仍不变，更新及验证说明见 [rc.11 发布说明](releases/v0.2.0-rc.11.md)。

rc.12 在额度查询完成时同步已核实的宿主账号状态，并提供查询、唤醒及候选生成任务的脱敏错误详情。保留 30 秒定时状态同步和原任务安全保护，数据库及接入层仍不变；详见 [rc.12 发布说明](releases/v0.2.0-rc.12.md)。

## 首次切换

当前 rc.14 重做统一任务记录并提供新的只读筛选路由。**后台及接入层均为 rc.14，首次从旧版更新必须显式 `--restart`，重启 CPA 注册路由；不能只替换后台。**数据库仍为 schema 9，从 rc.13 升级不增加迁移。更早版本升级仍须遵循下面的一致备份和降级限制，详见 [rc.14 发布说明](releases/v0.2.0-rc.14.md)。

rc.13 新增快捷唤醒与持久响应记录，数据库升级至 schema 9，首次启动自动迁移并保留现有任务及防重状态。升级前另存停机或 SQLite 在线一致备份；不能把旧后台直接换回迁移后的新库。原生接入层仍为 rc.8，详见 [rc.13 发布说明](releases/v0.2.0-rc.13.md)。

```sh
curl -fSL https://raw.githubusercontent.com/JayConstruct/codex-window-refresh/main/scripts/install-v2.sh -o /tmp/cwr-v2-install.sh
sudo bash /tmp/cwr-v2-install.sh --restart
```

root 会话可省略 sudo。首次下载需要已有 curl。脚本安装缺少的运行依赖，识别当前 CPA 的配置、进程、用户及 systemd 服务；无法唯一确认时用参数明确指定，例如：

```sh
sudo bash /tmp/cwr-v2-install.sh --cpa-dir /opt/cpa --service cliproxyapi --restart
```

用户服务也支持，例如 CPA 为 root 的用户服务：

```sh
sudo bash /tmp/cwr-v2-install.sh --cpa-dir /root/cliproxyapi --service cliproxyapi --user-service --user root --restart
```

使用 `--dry-run` 预览，不下载安装包、不写入或重启。`--version v0.2.0-rc.14` 固定版本；默认只选择 v2 发布。首次切换、清理旧服务环境及接入层二进制变化必须显式 `--restart`，脚本不会自动决定重启 CPA。首次重启同时回收旧版插件 Go 运行时映射。

## 后续更新

重新下载 V2 入口脚本，默认更新最新已发布的 V2 测试版：

```sh
curl -fSL -H 'Cache-Control: no-cache' https://raw.githubusercontent.com/JayConstruct/codex-window-refresh/main/scripts/install-v2.sh -o /tmp/cwr-v2-install.sh && sudo bash /tmp/cwr-v2-install.sh --version latest --restart
```

本次从旧版更新到 rc.14 会改变接入层，确认可重启 CPA 后须使用 `--restart`。以后若只改变后台与网页且接入层文件一致，可省略此参数仅重启后台；接入层改变仍在写入前要求显式重启。保留原部署所需的 `--cpa-dir`、用户服务等参数。若原命令固定了旧 `--version`，请替换为 `latest`，或指定本次 `v0.2.0-rc.14`。

`latest` 会按数值比较全部已发布 V2 rc 版本，不取发布列表第一条，也不使用排除预发布的 GitHub `/releases/latest`。下载的独立入口会重新获取两份 Python 安装器，不复用下载目录中的旧副本；只有完整源码目录（含上级 `go.mod`）使用本地安装器，运行前须自行更新源码。离线安装继续使用下文的包内 Python 入口。

**后台和接入层独立记录版本**。本次后台及接入层均为 rc.14；历史上后台 rc.13 使用 rc.8 接入层是正常复用，但不能用于本次新增路由。安装器会输出目标后台版本、目标接入层版本，成功后显示实际后台及接入层版本；也可在 V2 网页的诊断页查看后台版本。若安装器报告接入层变化、网络错误或验证失败，则尚未完成更新，不能仅凭下载成功判断。

普通 v1 的 `install.sh` 不自动选择 v2 包；检测到已有 v2 安装记录时拒绝覆盖。不能通过旧脚本把正在运行的 v2 改回 v1。

安装器完成以下核对后才报告成功：包的 SHA-256、ELF 架构、glibc 与协议；后台实际报告版本；接入层实际版本；后台消费的接入实例与当前 CPA 进程 PID；经 CPA 的公开资源入口返回的健康状态、版本与后台实例 ID。接入层 socket 已启动但 CPA 拒绝注册时，安装失败并回滚。安装验证不会查询上游或发起模型请求。生产环境仍需用户通过 CPA 页面验证真实管理认证及账号额度访问。

网页仍从 CPA 原入口 `/v0/resource/plugins/codex-window-refresh/status` 打开，不额外开放网络端口。刷新网页后使用 CPA 管理密钥连接；密钥只保存在页面内存中。

默认从 CPA 配置推断 HTTP(S) 监听地址。若须使用证书匹配的域名或其他可访问地址，可添加 `--cpa-url https://cpa.example.com:8317`；该地址不带路径或密钥，HTTPS 使用系统证书信任。健康检查仅返回后台就绪状态、版本和实例 ID，不访问账号或发送管理密钥。

## 文件与服务

在 CPA 目录下创建 `window-refresh-v2/`，包含当前后台文件、`data/`、`run/` 和安装记录。激活期间临时建立 `backups/`，成功后删除。`data/` 和 `run/` 由 CPA 用户拥有且权限为 0700；业务库权限 0600。临时恢复副本和安装记录仅 root 可读。已有路径权限不符合要求时拒绝覆盖。

创建同一 systemd 管理器中的 `window-refreshd-<配置路径摘要>.service`，以及 CPA 服务的 `75-window-refresh-v2.conf` drop-in，后者只设置 `CWR_V2_RUNTIME_DIR`。保留 CPA 主程序、主配置非 plugins 字段、账号目录与其他插件。清除本插件的 v1 策略、状态、环境文件、安装记录和备份，去掉包装中的旧字段与旧环境 drop-in；删除未选中的旧动态库和后台版本目录。当前选中的接入层可能版本号较早，但仍是正在使用的组件，会保留该文件。

先校验并下载完整包，再暂停需要切换的进程。更新前复制配置和安装文件；存在 SQLite 时通过在线备份接口创建一致副本。激活失败先停新后台，恢复文件与数据库，再启动旧服务。服务停止或恢复本身失败时停止操作并报告失败，不伪造更新成功。激活未完成时恢复副本位于 `window-refresh-v2/backups/`；新版本验证成功后清理旧版和所有临时恢复副本。清理失败时明确报告新版本已运行、清理未完成，不在删除旧数据后尝试回退；重新部署会继续处理待清理路径。

## 离线安装与失败恢复

下载对应架构包及同一发布的 `SHA256SUMS`，将包解压到临时目录，然后使用其中安装器：

```sh
python3 install-v2.py --cpa-dir /opt/cpa --service cliproxyapi \
  --version v0.2.0-rc.14 --package /path/codex-window-refresh-v2_v0.2.0-rc.14_linux_amd64.tar.gz \
  --checksums /path/SHA256SUMS --restart
```

以 root 运行。离线模式仍需预装依赖。安装器不接受自动降级数据库。失败且未完成自动恢复时，先停止后台和 CPA，再按临时 `backups/<本次安装>/index.json` 恢复文件，并恢复同一副本的 `backend.sqlite`（清除停机库旁的 `-wal/-shm`），最后 daemon-reload 并启动旧服务。成功部署后不保留旧数据与回退副本，不能再依赖部署前的 v1 数据回退。

容器或非 systemd 部署目前不使用此自动安装器。按 [原型运行说明](backend-v2-prototype.md) 构建或提取两个产物，挂载相同私有 socket 目录和 UID，为 CPA 设置 `CWR_V2_RUNTIME_DIR`，由已有编排器管理独立后台；首次替换接入层需重启 CPA。当前没有自动容器迁移或 v1 数据导入。
